| | head | feed | density | stocks |
|---|---|---|---|---|
| **B1** | 384 px = 48 mm | "top" (short way round) | 1–5 | WithGaps, Black, Transparent |
| **D11** | 96 px = 12 mm | "left" (long way round) | 1–3 | WithGaps, Transparent |

Both are recognised as families already. Two consequences worth writing down:

- **The 40 × 20 mm stock in the lab is a B1 label.** It is 320 × 160 px in the

- **The B1 does not understand `Continuous` stock**; the B21 does. The label

### §3.1 — the security finding — **fixed**

`c5d0515`. Only images are stored now, so an asset cannot be uploaded as HTML
and served as HTML from the app's own origin. Anything that is not an image is
served as `application/octet-stream` with `Content-Disposition: attachment` and
`nosniff`, which also covers assets stored before the allow-list existed. The
size limit is caught too, so the error shape the API documents is the one a
client receives.

A Content-Security-Policy is now sent by Caddy: everything is `'self'`, and
the one outside service — the ZPL preview, which sends the user's own label to
it — is named rather than the whole world being allowed. Checked in a browser:
the app loads, the fonts and the icon font load, the canvas draws, no
violations.

### §3.2 — a square label was turned instead of resized — **fixed**

`c5d0515`. The check that reads a changed size as the label turned a quarter
fitted every size, so a 40 × 40 label resized to 42 × 42 had its design
rotated. A round label is square by definition, so it was affected throughout.

The decision now lives on its own (`web/src/utils/label_turn.ts`), away from
the canvas, so it can be checked without one:

```
40 x 20 -> 20 x 40 is a turn
40 x 20 -> 42 x 21 is not a turn
40 x 40 -> 42 x 42 is not a turn, though the size is nearly square
a round label, which is square by definition, is not turned by a resize
a label that is nearly square is left alone, because a turn and a resize cannot be told apart
```

The last one is the trade-off: a label within a fifth of square is never read
as turned, because for a label that shape the two cannot be told apart from
the sizes alone.

### 0.7 Two changes since this follow-up was written

**Every NIIMBOT, not two families** (PR #3, merged). The family gate was two
hand-written sets of model names, and it let the app design for 15 of the 77
models the library describes. It carried no information: there are only 20
distinct geometries in that table and each is fully described by head dots,
feed direction and resolution, all of which the printer already reports. The
gate is gone, the size buttons are worked out from the head instead of two
hand-written lists, and the protocol is asked for per model rather than
guessed per family — a model nothing can resolve now refuses the batch rather
than being sent another printer's packets. `TemplateModelSchema` is a free
string on both sides: the server never talks to a printer and so should keep
no model list. 77 of 77 accepted, checked in `check-print-limits.mjs`.

**The label starts from the spreadsheet.** Uploading a CSV lays out one field
per column, showing a real value from a chosen row; a per-field switch decides
whether the heading is printed and it can be reworded. Date, serial and a new
`{operator}` field sit beside them. This retired the old design-time CSV path
entirely — the textarea, the persisted `csvData`, `csv` inside a saved
template, the print preview's own batch engine and the `d3-dsv` dependency.
There were two unrelated CSV implementations, which is why the app could ask
for the same file twice and then disagree with itself about what was in it.

Two notes for whoever picks this up:

- **`{operator}` is not a login, and the UI says so.** The app has no users —
  `authMode` is `none`, there is no session and no `/api/me` — so the field is
  a per-workstation name kept in that browser. If real authentication is added
  later, `{operator}` is the variable to fill from it.
- **§3.4's key count has moved.** English is now 517 keys, six of which were
  deleted from every dictionary along with the feature they described. The
  33 new keys are English-only, so the percentages are slightly worse than the
  figures above. The finding is unchanged: missing keys fall back to English.

**Still not printed.** Nothing in §3a has been run. The CSV fields were

### 0.5 Ready for a central server?

**Yes — with one caveat, and it is not a code problem.**

Everything in §1 and in this follow-up is on `main`, CI is green, and the
checks cover the two printers in the lab off the library's own model table.
A server install is `docker compose up -d` and the browser trust step; the
guide is `docs/PRODUCTION-INSTALL.md`.

The caveat: **nothing has been printed.** Every conclusion in this document
comes from running the real source modules under test. The §10 hardware
checklist is still unexecuted, and it is the only thing that turns "verified
by test" into "verified". Before the lab relies on it, three things need a
physical print:

1. **The B1 with a 40 × 20 mm roll.** The width check must pass (40 mm into a
   48 mm head) and the label must land where it should. This is the case the
   backing-paper fix was made for, and it is the one to prove.
2. **The D11 with a 12 mm roll.** A 40 mm label must be *blocked* on a 12 mm
   head, and a 12 mm one must print.
3. **One roll read of the tag.** The app warns before printing when the
   printer cannot read the roll's tag or its counter has run out. If that
   warning fires on a good roll, the warning is wrong and the print is
   refused for the wrong reason.

Also worth doing once, because of the change in §1.2: any browser that
connected to the printer **before** that fix still has the backing-paper width
in its local storage, and the fix stops it being re-applied but does not
remove it. On such a browser: hard-reload, then set the label size back to
40 × 20 mm — or, easier, connect the printer and use the *apply loaded size*
button in the connector, which now reads the media correctly.

### 0.6 One thing to know about error 20

Separate from this review, and worth recording because it is the most common
complaint about this printer and the least obvious from its name.

**Error 20 is not about the label.** Every NIIMBOT roll carries a small NFC
tag holding the label's size and how many labels are left, and the printer
writes the count back when a print finishes. Error 20 means that write
failed, so the printer refused the job. The usual causes are plain thermal
paper with no tag, a tag that has been damaged or removed, or a counter that
has run out.

It is the printer's own bookkeeping, so **there is no setting in the app that
turns it off** — the protocol has no command to skip the write. The upstream
project says the same: printing on paper without a tag needs firmware or
hardware changes.

What the app now does instead is look at what the printer already reports —
whether it could read the tag, whether the counter has run out — and warn
*before* the print, and explain the failure in words when it happens. See
`web/src/utils/printer_errors.ts`.

## 1. What was fixed

### 1.1 Width was measured in the wrong unit — `3d52b24`

**Files:** `web/src/utils/batch_printer.ts`, `web/src/components/dialogs/PrintPreview.svelte`

Both print paths measured the outgoing raster with `labelProps.dpmm` — the *template's*
resolution. By that point the canvas has already been through `resampleToDpmm` and is in
the *printer's* dots. Dividing the printer's pixels by the template's dpmm is a unit
error: for any template drawn above 8 dpmm it under-reports the width, and an over-wide
raster would have been let through to the printer.

Both now divide by `NIIMBOT_DPMM`, which is what the resampled canvas is actually in.

This is latent today — every stored template is `dpmm: 8`, so `resampleToDpmm` is a
no-op and the two numbers agree. It becomes real the moment a 300 dpi `_PRO` template
exists.

### 1.2 Backing paper was being taken for a label — `45b2d71`

**Files:** `web/src/utils/printer_profile.ts`, `web/src/components/LabelDesigner.svelte`,
`web/src/components/PrinterConnector.svelte`

This is the bug that stopped printing in the field. Reported as:

> Printing is blocked: the label is wider than the print head.
> Label width is too big for your printer: 50 mm > 48 mm

with a 40 mm × 20 mm label loaded in a B21.

The sensor behind the print head measures the **media**, not the label on it. A 40 mm
label on a 50 mm liner reports 50 mm. `applyLoadedLabel` took that at face value, resized
the canvas to 50 mm across, and the width check — correctly — then refused to print 50 mm
through a 48 mm head. The printer's own reading was blocking the printer.

Reproduced exactly against the real modules:

```
printer reports paperWidth=50 paperHeight=20   (the liner it sits on)
   canvas applied : 400 x 160 px
   across the head: 50 mm
   print button   : BLOCKED -> "50 mm > 48 mm"
```

The fix adds `loadedLabelFor(printer, paperInfo)` beside the existing `loadedLabelOf`:

```ts
const loaded = loadedLabelOf(paperInfo);
if (loaded === undefined) return undefined;
if (printer !== undefined && loaded.acrossMm > printer.headMm) return undefined;
return loaded;
```

`loadedLabelOf` stays what it was — *what the sensor measured* — and the new helper answers
*could this printer have that*, which needs the printer as well as the reading. A width
wider than the print head cannot be a label width, so it is ignored and the user's own size
is left alone, exactly the way an impossible length already was (`> 300 mm`).

**Both paths now agree.** `PrinterConnector`'s manual *apply loaded size* button used to
clamp an over-wide reading down to the head instead. That unblocked printing while laying
the design out on a label 8 mm wider than the one in the machine — arguably worse than the
block. It goes through the same helper now, and the clamp it no longer needs is gone.

Seven regression checks cover it, driven off `niimbluelib`'s own model table:

```
a reading the printer could not actually have
  ok    a 40 mm label on a B21 -> believed
  ok    the 50 mm liner it sits on -> wider than the 48 mm head, so ignored
  ok    exactly 48 mm on a 48 mm head -> still a label
  ok    a 12 mm roll on a D11 -> believed
  ok    a 15 mm reading on a D11's 12 mm head -> ignored
  ok    no printer -> nothing to compare the width with, so the reading stands
  ok    an impossible length is still ignored
```

### 1.3 CSV batch printing ignored the printer's capabilities — `3d52b24`

**File:** `web/src/components/dialogs/CsvBatchControl.svelte`

Two separate defects in one dialog:

- **Density was hard-coded 1–5.** A D11 accepts 1–3. A batch run at density 4 or 5 on a
  D11 is rejected by the printer. The slider now reads `densityMin`/`densityMax` off the
  connected printer's profile, and an out-of-range value is clamped by an `$effect` when
  the printer changes under it.
- **Label type was hard-coded `LabelType.WithGaps`.** A printer that does not understand
  that stock rejects the job outright with `SetPaperFail` (error 17). It now goes through
  the same `resolveLabelType(profile, rfidConsumablesType, requested)` the single-label
  path uses — the roll's own RFID tag first, filtered to what the printer says it
  understands.

The single-label path had both of these right. The batch path had drifted.

### 1.4 Dead code contradicting its own comments — `3d52b24`

**File:** `web/src/utils/label_fit.ts`

`turnContent` was exported, documented as the function that rotates a design when the
label is turned, and called from nowhere. The review's first recommendation was to decide
which design was intended and make one of them true.

Reading `5c3fc91` ("Keep the canvas the design, not the paper") changed that answer: the
turn was removed **deliberately**, because `adaptContentToLabel` already turns the content
and calling both would turn it twice. So the function was deleted and the comments
corrected, with a note explaining why no such helper exists. **No turn was re-added.**

### 1.5 Twelve lint errors, and the reason they collected

**Files:** nine under `web/src`, plus `web/eslint.config.js` and
`.github/workflows/ci.yml`

CI ran `typecheck`, `test`, `sv-check`, `build` and `check-limits` — not `lint`. Nothing
enforced it, so twelve errors accumulated. They are cleared and `npm run lint` now runs in
the web job, before `sv-check`, so the count cannot climb again.

Nine were dead weight and were simply removed: two unused imports in `PrintPreview`
(`printerInfo`, `logError`), an unused `id` in a `PreflightPanel` default no-op, an unused
`index` parameter on `describeUsbDevice`, a `reduce` in `CsvBatchControl` that ignored the
value it folded over (now `targets.length * copiesPerRow`, which is what it computed), and
an `$effect` in `LabelDesigner` whose body was an empty `if` — upstream leftover from the
niimblue vendoring, and the only read of `currentDialog` outside the template.

Three needed a judgement rather than a deletion:

- **Two keyless `{#each}` blocks.** `DATE_TIME_FORMATS` is a frozen list of unique strings,
  so it is keyed by the string. `parseErrors` is not — the same message can come back for
  several rows — so it is keyed by index, which is correct for a list rebuilt whole.
- **`_ignored` in `SavedLabelsMenu` (x2).** `const { id: _ignored, ...rest }` is the
  deliberate idiom for dropping the server id from an imported template. The convention was
  right and the config did not know about it, so the underscore patterns were added to
  `@typescript-eslint/no-unused-vars` rather than the code being bent to suit the rule.

Two are rules that are wrong about runes, and carry a targeted disable with the reason:

- **`prefer-svelte-reactivity` on a `Map` in `LabelDesigner`.** It is built and discarded
  inside one function call. Nothing observes it; what the template renders from is the
  reassignment at the end. A `SvelteMap` would make a reactive object for one loop and
  throw it away.
- **`no-unused-expressions` on `editRevision;` in `LinkedObjectControl`.** The bare read is
  the subscription — it is what makes the derived rebuild after a canvas edit. Deleting it
  would silence the rule and break the component.

## 3. Still open

Nothing here blocks printing. They are listed in the order I would do them.

### 3.1 Assets are served with their uploaded `Content-Type`, and there is no CSP — **security**

`app/src/routes/api.ts:143` echoes the stored MIME type straight back:

```ts
return reply.header("Content-Type", asset.mime).send(assets.read(asset));
```

Nothing restricts the type on upload, so an authenticated user can store `text/html` and
get it served as HTML from the app's own origin. That is stored XSS against a page that
holds the API key and the printer's device grants. There is no CSP anywhere — neither
`@fastify/helmet` in the app nor a header in `deploy/caddy/Caddyfile` — so nothing
mitigates it in depth.

**Fix:** allow-list image MIME types on upload; serve anything else as
`application/octet-stream` with `Content-Disposition: attachment` and
`X-Content-Type-Options: nosniff`; add a CSP in Caddy.

Mitigating today: single-tenant LAN deployment, authenticated uploads only. It is still
the most serious thing left.

### 3.2 Turn detection misfires on square and near-square labels — **correctness**

`web/src/utils/label_fit.ts:289`:

```ts
const turned =
  Math.abs(newSize.width / oldSize.height - 1) < 0.2 &&
  Math.abs(newSize.height / oldSize.width - 1) < 0.2 &&
  Math.abs(newSize.width - oldSize.width) > 1;
```

For a label that is roughly square, *every* resize satisfies the first two conditions, so
any change bigger than one pixel is read as a quarter turn and the content is rotated 90°.
Resize a 40 × 40 label to 42 × 42 and the design turns. Round labels are square by
definition, so they are affected throughout.

**Fix:** require the aspect ratio to have actually inverted — add a guard that the old
size was not already near-square, e.g. `Math.abs(oldSize.width / oldSize.height - 1) > 0.2`.

### 3.3 Lint — **resolved, see 1.5**

Was: 12 errors outstanding and `npm run lint` absent from CI. Both fixed.

### 3.4 Translation coverage is between 0% and 48% — **polish**

### 3.5 `LABELBENCH_IP` is absent from `.env` — **deployment**

`docker-compose.yml:43` and `deploy/caddy/Caddyfile:41,142,143` all reference it, each with
a hard-coded `10.10.17.185` default. `.env` does not set it. So the committed IP is what
Caddy will serve on unless the operator notices.

This matters more than it looks: **device grants are origin-specific.** A printer granted
at `https://labelbench.local:8443` is not granted at `https://10.10.17.185:8443`, and a
grant does not carry between ports. A wrong IP silently means a second origin where every
printer has to be re-granted.

**Fix:** add `LABELBENCH_IP` to `.env` and to `.env.example`; have `deploy/prepare-host.sh`
write it (it already detects the address at line 109).

### 3.6 The `too_large` branch is unreachable — **tidiness**

`app/src/routes/api.ts:133`:

```ts
if (bytes.length > maxBytes) {
  return reply.code(413).send({ error: "too_large", max_bytes: maxBytes });
}
```

`@fastify/multipart` is registered with `limits: { fileSize: config.maxAssetBytes }`
(`app/src/server.ts:67`), so `file.toBuffer()` throws before this line is ever reached. The
client gets Fastify's own error shape, not `{"error":"too_large"}`.

**Fix:** catch the multipart error and map it to this response, so the documented shape is
the one clients actually receive. Harmless either way.

### 3.7 Nit — duplicated comment

`web/src/utils/printer_profile.ts:152–156` has the same two-line comment twice. Predates
this work; left alone to keep the fix commits focused.

## 3a. The hardware checklist for this lab

The §10 checklist in the review spec is generic. This is the same thing with
the numbers that matter here, and it is the part that is not done.

### The B1 (48 mm head)

- [ ] A 40 × 20 mm roll loads. The app shows "40 × 20 mm" for the loaded
      media, and the canvas becomes 320 × 160 px.
- [ ] A print of one label succeeds. The label is the right way up and the
      right way round — the text reads along the 40 mm, not down it.
- [ ] The counter on the roll goes **up by one** after the print, so the
      printer wrote the count back to the tag. This is the write that error
      20 is about.
- [ ] The roll's usage in the connector shows the same number.
- [ ] A second print succeeds, and the counter goes up by one again.
- [ ] The **backing paper** case: if the label sits on a wider liner, the app
      must not take the liner's width for the label's. The print should work
      and the canvas should stay 320 × 160 px.
- [ ] A label wider than 48 mm is blocked with "60 mm > 48 mm", and the
      button is disabled.

### The D11 (12 mm head)

- [ ] A 12 mm roll loads. The canvas becomes 160 × 320 px — the same label,
      held the other way round, because the D11 feeds it the long way.
- [ ] A 40 × 20 mm label is **blocked** with "40 mm > 12 mm". The D11 cannot
      print a 40 mm label, and the app must say so rather than sending it.
- [ ] A 12 mm label prints.
- [ ] The density slider offers 1–3, not 1–5. A D11 rejects 4 and 5.

### Both

- [ ] The **roll's tag**: a good roll must not produce a warning in the print
      preview. If it does, the warning is wrong.
- [ ] Plain thermal paper with no tag must produce a warning, and the print
      must fail with error 20 — explained in words, not as a number.
- [ ] The app's own log (`Debug`) shows the packets for one print, so a
      failure can be read rather than guessed at.

### The order that finds the most

1. The B1 with a good NIIMBOT roll — everything else depends on this one.
2. The counter going up by one, which is the thing error 20 is about.
3. The D11 with a 12 mm roll.
4. The blocked 40 mm label on the D11.

## 5. One thing to know about the deployed app

`applyLoadedLabel` goes through `onUpdateLabelProps`, which calls `saveLastLabelProps`
(`LabelDesigner.svelte:290`), and the designer restores that on startup
(`loadLastLabelProps`, `:802`). So any browser that connected to the printer *before* this
fix has a 50 mm canvas in its local storage, and the fix stops it being re-applied but does
not remove it.

Anyone on such a browser needs to, once: hard-reload, then set the label size back to
40 × 20 mm, or load a template stored at the right size.
