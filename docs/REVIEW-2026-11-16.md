## 1. What was fixed

### 1.1 Width was measured in the wrong unit — `3d52b24`

**Files:** `web/src/utils/batch_printer.ts`, `web/src/components/dialogs/PrintPreview.svelte`

Both print paths measured the outgoing raster with `labelProps.dpmm` — the *template's*
resolution. By that point the canvas has already been through `resampleToDpmm` and is in
the *printer's* dots. Dividing the printer's pixels by the template's dpmm is a unit
error: for any template drawn above 8 dpmm it under-reports the width, and an over-wide
raster would have been let through to the printer.

Both now divide by `NIIMBOT_DPMM`, which is what the resampled canvas is actually in.

This is latent today — every stored template is `dpmm: 8`, so `resampleToDpmm` is a
no-op and the two numbers agree. It becomes real the moment a 300 dpi `_PRO` template
exists.

### 1.2 Backing paper was being taken for a label — `45b2d71`

**Files:** `web/src/utils/printer_profile.ts`, `web/src/components/LabelDesigner.svelte`,
`web/src/components/PrinterConnector.svelte`

This is the bug that stopped printing in the field. Reported as:

> Printing is blocked: the label is wider than the print head.
> Label width is too big for your printer: 50 mm > 48 mm

with a 40 mm × 20 mm label loaded in a B21.

The sensor behind the print head measures the **media**, not the label on it. A 40 mm
label on a 50 mm liner reports 50 mm. `applyLoadedLabel` took that at face value, resized
the canvas to 50 mm across, and the width check — correctly — then refused to print 50 mm
through a 48 mm head. The printer's own reading was blocking the printer.

Reproduced exactly against the real modules:

```
printer reports paperWidth=50 paperHeight=20   (the liner it sits on)
   canvas applied : 400 x 160 px
   across the head: 50 mm
   print button   : BLOCKED -> "50 mm > 48 mm"
```

The fix adds `loadedLabelFor(printer, paperInfo)` beside the existing `loadedLabelOf`:

```ts
const loaded = loadedLabelOf(paperInfo);
if (loaded === undefined) return undefined;
if (printer !== undefined && loaded.acrossMm > printer.headMm) return undefined;
return loaded;
```

`loadedLabelOf` stays what it was — *what the sensor measured* — and the new helper answers
*could this printer have that*, which needs the printer as well as the reading. A width
wider than the print head cannot be a label width, so it is ignored and the user's own size
is left alone, exactly the way an impossible length already was (`> 300 mm`).

**Both paths now agree.** `PrinterConnector`'s manual *apply loaded size* button used to
clamp an over-wide reading down to the head instead. That unblocked printing while laying
the design out on a label 8 mm wider than the one in the machine — arguably worse than the
block. It goes through the same helper now, and the clamp it no longer needs is gone.

Seven regression checks cover it, driven off `niimbluelib`'s own model table:

```
a reading the printer could not actually have
  ok    a 40 mm label on a B21 -> believed
  ok    the 50 mm liner it sits on -> wider than the 48 mm head, so ignored
  ok    exactly 48 mm on a 48 mm head -> still a label
  ok    a 12 mm roll on a D11 -> believed
  ok    a 15 mm reading on a D11's 12 mm head -> ignored
  ok    no printer -> nothing to compare the width with, so the reading stands
  ok    an impossible length is still ignored
```

### 1.3 CSV batch printing ignored the printer's capabilities — `3d52b24`

**File:** `web/src/components/dialogs/CsvBatchControl.svelte`

Two separate defects in one dialog:

- **Density was hard-coded 1–5.** A D11 accepts 1–3. A batch run at density 4 or 5 on a
  D11 is rejected by the printer. The slider now reads `densityMin`/`densityMax` off the
  connected printer's profile, and an out-of-range value is clamped by an `$effect` when
  the printer changes under it.
- **Label type was hard-coded `LabelType.WithGaps`.** A printer that does not understand
  that stock rejects the job outright with `SetPaperFail` (error 17). It now goes through
  the same `resolveLabelType(profile, rfidConsumablesType, requested)` the single-label
  path uses — the roll's own RFID tag first, filtered to what the printer says it
  understands.

The single-label path had both of these right. The batch path had drifted.

### 1.4 Dead code contradicting its own comments — `3d52b24`

**File:** `web/src/utils/label_fit.ts`

`turnContent` was exported, documented as the function that rotates a design when the
label is turned, and called from nowhere. The review's first recommendation was to decide
which design was intended and make one of them true.

Reading `5c3fc91` ("Keep the canvas the design, not the paper") changed that answer: the
turn was removed **deliberately**, because `adaptContentToLabel` already turns the content
and calling both would turn it twice. So the function was deleted and the comments
corrected, with a note explaining why no such helper exists. **No turn was re-added.**

## 3. Still open

Nothing here blocks printing. They are listed in the order I would do them.

### 3.1 Assets are served with their uploaded `Content-Type`, and there is no CSP — **security**

`app/src/routes/api.ts:143` echoes the stored MIME type straight back:

```ts
return reply.header("Content-Type", asset.mime).send(assets.read(asset));
```

Nothing restricts the type on upload, so an authenticated user can store `text/html` and
get it served as HTML from the app's own origin. That is stored XSS against a page that
holds the API key and the printer's device grants. There is no CSP anywhere — neither
`@fastify/helmet` in the app nor a header in `deploy/caddy/Caddyfile` — so nothing
mitigates it in depth.

**Fix:** allow-list image MIME types on upload; serve anything else as
`application/octet-stream` with `Content-Disposition: attachment` and
`X-Content-Type-Options: nosniff`; add a CSP in Caddy.

Mitigating today: single-tenant LAN deployment, authenticated uploads only. It is still
the most serious thing left.

### 3.2 Turn detection misfires on square and near-square labels — **correctness**

`web/src/utils/label_fit.ts:289`:

```ts
const turned =
  Math.abs(newSize.width / oldSize.height - 1) < 0.2 &&
  Math.abs(newSize.height / oldSize.width - 1) < 0.2 &&
  Math.abs(newSize.width - oldSize.width) > 1;
```

For a label that is roughly square, *every* resize satisfies the first two conditions, so
any change bigger than one pixel is read as a quarter turn and the content is rotated 90°.
Resize a 40 × 40 label to 42 × 42 and the design turns. Round labels are square by
definition, so they are affected throughout.

**Fix:** require the aspect ratio to have actually inverted — add a guard that the old
size was not already near-square, e.g. `Math.abs(oldSize.width / oldSize.height - 1) > 0.2`.

### 3.4 Translation coverage is between 0% and 48% — **polish**

Against `en.json`'s 491 keys:

```
ru 48%   ar 46%   de 46%   it 44%   uk 44%   zh_cn 39%   cs 38%   pl 38%
es 37%   bg 36%   hi 36%   mr 36%   hr 34%   hu 33%   pt_BR 33%   tr 33%
```

`id.json` is an empty object — the language appears in the picker and resolves to nothing
but English. Missing keys fall back to English, so nothing breaks; the UI is just mixed.

**Fix:** at minimum drop `id` from the picker until it has content. Decide whether partial
locales should be offered at all.

### 3.5 `LABELBENCH_IP` is absent from `.env` — **deployment**

`docker-compose.yml:43` and `deploy/caddy/Caddyfile:41,142,143` all reference it, each with
a hard-coded `10.10.17.185` default. `.env` does not set it. So the committed IP is what
Caddy will serve on unless the operator notices.

This matters more than it looks: **device grants are origin-specific.** A printer granted
at `https://labelbench.local:8443` is not granted at `https://10.10.17.185:8443`, and a
grant does not carry between ports. A wrong IP silently means a second origin where every
printer has to be re-granted.

**Fix:** add `LABELBENCH_IP` to `.env` and to `.env.example`; have `deploy/prepare-host.sh`
write it (it already detects the address at line 109).

### 3.6 The `too_large` branch is unreachable — **tidiness**

`app/src/routes/api.ts:133`:

```ts
if (bytes.length > maxBytes) {
  return reply.code(413).send({ error: "too_large", max_bytes: maxBytes });
}
```

`@fastify/multipart` is registered with `limits: { fileSize: config.maxAssetBytes }`
(`app/src/server.ts:67`), so `file.toBuffer()` throws before this line is ever reached. The
client gets Fastify's own error shape, not `{"error":"too_large"}`.

**Fix:** catch the multipart error and map it to this response, so the documented shape is
the one clients actually receive. Harmless either way.

## 5. One thing to know about the deployed app

`applyLoadedLabel` goes through `onUpdateLabelProps`, which calls `saveLastLabelProps`
(`LabelDesigner.svelte:290`), and the designer restores that on startup
(`loadLastLabelProps`, `:802`). So any browser that connected to the printer *before* this
fix has a 50 mm canvas in its local storage, and the fix stops it being re-applied but does
not remove it.

Anyone on such a browser needs to, once: hard-reload, then set the label size back to
40 × 20 mm, or load a template stored at the right size.
